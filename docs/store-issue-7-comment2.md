I ran the package against all seven gates rather than assuming it passed. Four held. Three did not, and they are fixed in `dsh-overlay-check@0.3.0` — with the caveat that finding them by testing against your list is exactly the argument for having the list, so thank you for writing it that precisely.

**Gate 6, symlink confinement — this one was a real hole.** My containment was lexical: reject `..`, reject absolute paths elsewhere. A symlink *inside* the root pointing out of it passes that check cleanly, and I was following it. A crafted link in a profile could have been read at capture and written at restore, outside the transaction root it claimed to be confined to. Now both the path and its nearest existing ancestor are resolved before either is trusted, and the check runs again at write time because a tree can gain a symlink between capture and restore.

Worth flagging the subtlety in case you implement it locally: an absent file has no realpath, so it resolves to its nearest existing ancestor — for a new file directly under the root, that is the root itself. Treating that as an escape breaks the absent-file case entirely, which is the case the snapshot exists for on a fresh profile. I got that backwards for one commit.

**Gate 4, interrupted restore — retryable in principle, not in fact.** My temp file was named per process, so a restore that died between write and rename left a temp that made the retry throw `EEXIST`. Idempotent right up until the interruption that matters. Temp names are now unique per attempt; tests cover both a leftover temp and restoring twice in a row.

**Gate 5, evidence retention — identity yes, boundary no.** Evidence had its own snapshot id, but pruning treated it like any routine capture, so a policy of "keep the last N" could discard the record of the failed transaction while keeping twenty successful ones. Snapshots now carry a `kind`, and captures and evidence prune on separate budgets: `pruneSnapshots(store, 20)` bounds captures and leaves evidence alone; `{ captures, evidence }` bounds both.

**Gates 1, 2, 3 and 7 held as written**, and now have tests named after them. Gate 7 I verified rather than asserted: no lifecycle scripts, no dependencies, and the only `child_process` match in the source is a comment saying it does not spawn one. Gate 1 has a test that the capture set is exactly the paths passed and nothing else — no discovery, no globbing.

If the Store keeps sequencing, provenance, boot and promotion, the library's whole surface is `takeSnapshot` / `diffAgainstSnapshot` / `restoreSnapshot` plus `preflightOps`, and a thin adapter in your codebase may be a better fit than a dependency — in which case the test matrix is the useful artifact and you should feel free to reimplement against it. I care about the gates being enforced somewhere, not about whose code enforces them.
